# MongoDB Index Implementation Report

## Summary

Three indexes were added across two model files to eliminate collection scans (COLLSCAN) on the most frequently queried paths in the application — user order history, product catalogue browsing, and product URL lookups. No business logic, controllers, routes, middleware, or API responses were changed. Only schema index definitions were added.

---

## Files Modified

| File | Change |
|------|--------|
| `backend/src/models/orderModel.js` | Added single-field index on `user` |
| `backend/src/models/productModel.js` | Added unique sparse index on `slug`; added compound index on `(isActive, category)` |

## Indexes Added

### 1. `Order.user` — Single-Field Index

```js
orderSchema.index({ user: 1 });
```

| Property | Value |
|----------|-------|
| **Collection** | `orders` |
| **Type** | Single-field, ascending |
| **Field** | `user` (ObjectId reference to User) |
| **Unique** | No |

**Purpose:**
Every order belongs to one user. Without this index, fetching a user's orders requires MongoDB to examine every document in the `orders` collection to find the matching ones — a full COLLSCAN. With this index, MongoDB jumps directly to only the documents for that user.

**Queries improved:**

`getMyOrders()` — `orderController.js`
```js
Order.find({ user: req.user.id }).sort({ createdAt: -1 })
```

`cancelOrder()` — `orderController.js`
```js
Order.findById(id).session(session)
// After cancellation, stock restoration iterates order.items
```

Purchase verification in `addReview()` — `reviewController.js`
```js
Order.findOne({
  user: req.user.id,
  items: { $elemMatch: { product: product._id } }
})
```
This query verifies a user actually bought a product before they can review it. Without the `user` index it scans the entire orders collection for every review submission.

### 2. `Product.slug` — Unique Sparse Index

```js
productSchema.index({ slug: 1 }, { unique: true, sparse: true });
```

| Property | Value |
|----------|-------|
| **Collection** | `products` |
| **Type** | Single-field, unique, sparse |
| **Field** | `slug` (String, auto-generated from product name) |
| **Unique** | Yes |
| **Sparse** | Yes — skips documents where `slug` is null/undefined |

**Purpose:**
The `slug` field is generated by a `pre("save")` hook that converts a product name into a URL-friendly string (e.g., `"Nike Air Max 270"` → `"nike-air-max-270"`). SEO-friendly product URLs take the form `/products/nike-air-max-270`. A frontend querying by slug would run `Product.findOne({ slug: "..." })` — without an index this is a COLLSCAN over the entire products collection on every product page load.

The index is `sparse: true` because any product documents that existed before the slug hook was introduced will have `slug: null`. A non-sparse unique index would treat all nulls as equal — meaning only one null-slug document could exist. `sparse: true` simply skips null values entirely.

**Queries improved:**
```js
// Future/frontend query — product page by SEO URL
Product.findOne({ slug: "nike-air-max-270" })
```

Additionally, the unique constraint ensures no two products can receive the same slug, preventing duplicate URL collisions at the database level (rather than relying on application logic).

### 3. `Product.(isActive, category)` — Compound Index

```js
productSchema.index({ isActive: 1, category: 1 });
```

| Property | Value |
|----------|-------|
| **Collection** | `products` |
| **Type** | Compound, ascending on both fields |
| **Fields** | `isActive` (Boolean), `category` (String) |
| **Unique** | No |

**Purpose:**
`isActive` is a soft-delete flag — deactivated products stay in the database for order history but must be hidden from the catalogue. Every catalogue query filters by `isActive: true`. `category` is the primary browse dimension. A compound index on both fields means MongoDB can resolve the full query `{ isActive: true, category: "Electronics" }` entirely from the index without opening any product documents until the final fetch.

The field order follows the **ESR rule** (Equality → Sort → Range): `isActive` is an equality filter (always compared with `true`/`false`), so it goes first. `category` is also an equality filter and goes second.

The index satisfies the **prefix rule** — it can be used by queries that include only the leftmost field:

| Query | Index used? |
|-------|-------------|
| `{ isActive: true }` | ✅ — leftmost prefix |
| `{ isActive: true, category: "Electronics" }` | ✅ — both fields |
| `{ category: "Electronics" }` | ❌ — skips leftmost field; existing single `category` index used instead |

**Relationship to existing `category` index:** The schema already declares `index: true` on the `category` field. That single-field index remains useful for queries that filter only by category without an `isActive` filter. Both indexes coexist — they are not redundant.

**Queries improved:**

`getAllProducts()` — `productController.js`
```js
Product.find({ isActive: true })
// Uses leftmost prefix of the compound index
```

Future category-filtered queries:
```js
Product.find({ isActive: true, category: "Clothing" })
// Uses full compound index — most selective query shape
```

## Expected Performance Improvement

### COLLSCAN (before indexes)

```
Query: Order.find({ user: "abc123" })

MongoDB opens every document:
┌─────────────────────┐
│ doc 1  user: "xyz"  │ discard
│ doc 2  user: "pqr"  │ discard
│ doc 3  user: "abc123" │ KEEP
│ ...                 │
│ doc 20,000          │ discard
└─────────────────────┘
Examined: 20,000   Returned: 12   Efficiency: 0.06%
```

### IXSCAN (after index)

```
Query: Order.find({ user: "abc123" })

MongoDB consults B-tree index:
"abc123" → [ptr_3, ptr_99, ptr_145 ... 12 entries]
         ↓
Fetch only those 12 documents

Examined: 12   Returned: 12   Efficiency: 100%
```

For a store with 1,000 users each placing 20 orders (20,000 total orders), the `user` index reduces documents examined from 20,000 to ~20 per `getMyOrders` call — a **1,000× improvement** that scales linearly as order volume grows.

## Query Impact

| Query | Controller | Index used | Before | After |
|-------|-----------|-----------|--------|-------|
| `Order.find({ user: id }).sort(...)` | `getMyOrders` | `Order.user` | COLLSCAN all orders | IXSCAN → user's orders only |
| `Order.findOne({ user: id, items: $elemMatch... })` | `addReview` (purchase verify) | `Order.user` | COLLSCAN all orders | IXSCAN → user's orders only |
| `Product.find({ isActive: true })` | `getAllProducts` | `(isActive, category)` prefix | COLLSCAN all products | IXSCAN → active products only |
| `Product.findOne({ slug: "..." })` | Future/frontend | `slug` unique | COLLSCAN all products | IXSCAN → 1 document |
| `Product.find({ isActive: true, category: x })` | Future/category filter | `(isActive, category)` full | COLLSCAN all products | IXSCAN → filtered subset |

## Verification

After the application is running with a connected MongoDB instance, verify each index using `.explain("executionStats")`.

### Verify Order.user index

```js
const result = await Order
  .find({ user: "paste-a-real-user-id-here" })
  .explain("executionStats");

console.log(result.queryPlanner.winningPlan.stage);
// Expected: "FETCH"

console.log(result.queryPlanner.winningPlan.inputStage.stage);
// Expected: "IXSCAN"  ← confirms index is used

console.log(result.executionStats.totalDocsExamined);
// Expected: equals totalDocsReturned (only matching docs examined)

console.log(result.executionStats.totalDocsReturned);
// Expected: the user's actual order count
```

### Verify Product.(isActive, category) index

```js
const result = await Product
  .find({ isActive: true })
  .explain("executionStats");

console.log(result.queryPlanner.winningPlan.inputStage?.stage
  ?? result.queryPlanner.winningPlan.stage);
// Expected: "IXSCAN"

console.log(result.executionStats.totalDocsExamined);
// Expected: only active products, not all products
```

### Verify Product.slug index

```js
const result = await Product
  .findOne({ slug: "some-product-slug" })
  .explain("executionStats");

console.log(result.queryPlanner.winningPlan.inputStage?.stage);
// Expected: "IXSCAN"

console.log(result.executionStats.totalDocsExamined);
// Expected: 0 or 1 (the single matching document)
```

### Key fields to read

| Field | Good value | Bad value |
|-------|-----------|-----------|
| `winningPlan.stage` or `winningPlan.inputStage.stage` | `IXSCAN` | `COLLSCAN` |
| `totalDocsExamined` | Equals `totalDocsReturned` | Much larger than `totalDocsReturned` |
| `executionTimeMillis` | Low (single-digit ms) | High (tens/hundreds of ms) |

### Checking indexes exist in MongoDB shell

```js
db.orders.getIndexes()
// Should include: { key: { user: 1 } }

db.products.getIndexes()
// Should include: { key: { slug: 1 }, unique: true, sparse: true }
// Should include: { key: { isActive: 1, category: 1 } }
```

## Index Synchronization Note

The project uses `syncIndexes()` only in `reviewModel.js` — specifically because that model's unique compound index must be enforced immediately and consistently across deployments.

`orderModel.js` and `productModel.js` do not use `syncIndexes()`, matching the project's existing per-model strategy. Mongoose will create the new indexes automatically on the **first connection** for fresh deployments. For existing databases with live data, run once manually:

```js
// In a one-time migration script or MongoDB shell
db.orders.createIndex({ user: 1 })
db.products.createIndex({ slug: 1 }, { unique: true, sparse: true })
db.products.createIndex({ isActive: 1, category: 1 })
```
